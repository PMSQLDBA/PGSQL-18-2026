## Topic 12: PostgreSQL Vacuum & Autovacuum

This topic is important for both **PostgreSQL production support and interviews**. The key idea is simple: because of PostgreSQL's MVCC design, old row versions remain in the table after `UPDATE` and `DELETE`. `VACUUM` is responsible for making that space reusable and preventing transaction-ID problems.

### 1. MVCC — Why PostgreSQL Needs VACUUM

PostgreSQL uses **MVCC (Multi-Version Concurrency Control)** so readers and writers can work concurrently without unnecessarily blocking each other.

When a row is updated, PostgreSQL normally does **not overwrite the existing row in place**. It creates a new row version.

For example:

```sql
UPDATE employees
SET salary = 90000
WHERE employee_id = 101;
```

Conceptually:

```text
Before UPDATE

employee_id | salary
------------+-------
101         | 80000    <-- old tuple

After UPDATE

101         | 80000    <-- old/dead tuple
101         | 90000    <-- new/live tuple
```

The old version may still be required by another transaction that started earlier. Once no active transaction can see that old version, it can eventually be cleaned up.

That old row version is commonly called a **dead tuple**.

---

## 2. Live Tuples vs Dead Tuples

A **live tuple** is a row version that is currently valid.

A **dead tuple** is an old row version that is no longer needed by any transaction.

Dead tuples are mainly generated by:

```sql
UPDATE
DELETE
```

A workload with frequent updates can therefore generate millions of dead tuples even if the total number of logical rows remains almost unchanged.

You can get estimates from:

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

A useful production query is:

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Remember that these tuple counts are **statistics/estimates**, not exact real-time counts.

---

## 3. What VACUUM Does

Basic command:

```sql
VACUUM employees;
```

Or:

```sql
VACUUM;
```

for the current database.

Regular `VACUUM` primarily identifies obsolete tuples and makes their space available for **reuse inside PostgreSQL**.

Think of it as:

```text
UPDATE / DELETE
       |
       v
Old row versions
       |
       v
Dead tuples
       |
       v
VACUUM
       |
       v
Space becomes reusable
```

An important distinction is:

```text
VACUUM
    -> makes space reusable internally
    -> normally does NOT return most table space to OS

VACUUM FULL
    -> rewrites/compacts table
    -> can return space to OS
    -> requires a much stronger table lock
```

For example:

```sql
VACUUM FULL employees;
```

`VACUUM FULL` should therefore **not** be treated as routine maintenance on a busy production table.

---

## 4. VACUUM vs ANALYZE

These solve different problems.

### VACUUM

Main purposes include:

* cleaning up obsolete row versions;
* making space reusable;
* maintaining the visibility map;
* helping index-only scans;
* protecting against transaction-ID wraparound.

Example:

```sql
VACUUM employees;
```

### ANALYZE

`ANALYZE` collects statistics used by the PostgreSQL query planner.

```sql
ANALYZE employees;
```

It collects information such as:

* approximate row counts;
* data distribution;
* common values;
* null fractions;
* column correlation and other planner statistics.

The optimizer uses these statistics to decide between plans such as:

```text
Sequential Scan
Index Scan
Bitmap Scan
Nested Loop
Hash Join
Merge Join
```

You can run both together:

```sql
VACUUM ANALYZE employees;
```

So remember:

> **VACUUM deals primarily with tuple/storage maintenance; ANALYZE deals primarily with optimizer statistics.**

---

## 5. What Is Autovacuum?

You normally don't want DBAs manually running `VACUUM` against every table.

PostgreSQL has an automatic maintenance system called **autovacuum**.

Check whether it is enabled:

```sql
SHOW autovacuum;
```

Normally:

```text
autovacuum
----------
on
```

Autovacuum workers automatically perform maintenance such as:

```text
VACUUM
ANALYZE
```

when tables cross configured thresholds.

---

## 6. When Does Autovacuum Trigger?

A simplified vacuum threshold is:

```text
vacuum threshold =
autovacuum_vacuum_threshold
+
autovacuum_vacuum_scale_factor × number of tuples
```

Suppose:

```text
autovacuum_vacuum_threshold = 50
autovacuum_vacuum_scale_factor = 0.20
table rows = 1,000,000
```

Then approximately:

```text
50 + (0.20 × 1,000,000)

= 200,050
```

So roughly 200,050 qualifying tuple changes/dead tuples can be enough to trigger vacuum under that simplified model.

This explains a common production problem with very large tables.

For a table with:

```text
500,000,000 rows
```

and:

```text
scale_factor = 0.20
```

the scale-factor portion alone is:

```text
100,000,000
```

Waiting for that much churn may be far too aggressive for a heavily updated table.

---

## 7. Autovacuum Tuning

Important settings include:

```sql
SHOW autovacuum_max_workers;
SHOW autovacuum_vacuum_threshold;
SHOW autovacuum_vacuum_scale_factor;
SHOW autovacuum_analyze_threshold;
SHOW autovacuum_analyze_scale_factor;
SHOW autovacuum_vacuum_cost_delay;
SHOW autovacuum_vacuum_cost_limit;
SHOW autovacuum_naptime;
```

You can also tune specific tables.

Example:

```sql
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor = 0.02,
    autovacuum_vacuum_threshold = 1000
);
```

For a high-write table, a smaller scale factor causes vacuum to become eligible earlier.

This is often better than changing the global setting because different tables can have completely different workloads.

## 8. Example Production Scenario

Suppose:

```text
orders table
------------
Rows: 200 million
Updates: millions/day
Deletes: frequent
```

You notice:

```text
High dead tuples
Table/index growth
Increasing I/O
Query performance degradation
Autovacuum struggling to keep up
```

The wrong reaction is simply:

```text
Disable autovacuum
```

A better investigation is:

```text
1. Check dead tuples
2. Check last autovacuum
3. Check long-running transactions
4. Check autovacuum activity
5. Check table-specific vacuum settings
6. Check whether workers/cost settings are limiting throughput
7. Check table and index bloat
8. Tune based on workload
```

For example:

```sql
SELECT
    pid,
    datname,
    relid::regclass,
    phase
FROM pg_stat_progress_vacuum;
```

# 9. Long-Running Transactions — Major VACUUM Problem

This is one of the most important production concepts.

Suppose:

```text
Transaction A starts
      |
      | remains open for hours
      |
Many UPDATE/DELETE operations happen
      |
VACUUM runs
```

VACUUM may not be able to remove old row versions that are still potentially visible to Transaction A's snapshot.

So you may see:

```text
Autovacuum is running
BUT
dead tuples keep accumulating
```

The actual root cause could be a **long-running transaction or old snapshot**, rather than insufficient autovacuum.

Useful investigation:

```sql
SELECT
    pid,
    usename,
    state,
    xact_start,
    query_start,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Pay particular attention to sessions that are:

```text
idle in transaction
```

for a long time.

# 10. Table Bloat

If dead tuples accumulate faster than vacuum can deal with them, tables and indexes may become unnecessarily large.

This is commonly referred to as **bloat**.

Effects can include:

```text
More disk space
More pages to read
More cache pressure
More I/O
Longer maintenance operations
Potentially slower queries
```

Regular `VACUUM` makes dead space reusable, but it does not generally shrink the physical file back to its minimum possible size.

That distinction is important:

```text
Table file = 100 GB

VACUUM
    |
    +--> dead space becomes reusable
    |
    +--> file may remain around 100 GB
```

If substantial physical shrinking is required, options may include `VACUUM FULL` or other table-rewrite/reorganization approaches, depending on operational constraints.

---

# 11. Transaction IDs — XIDs

Every PostgreSQL transaction is associated with a transaction ID conceptually known as an **XID**.

Tuple visibility depends heavily on transaction information.

Simplified tuple metadata can be thought of as:

```text
xmin -> transaction that created tuple
xmax -> transaction that deleted/invalidated tuple
```

Example:

```text
Tuple
--------------------
employee_id = 101
salary      = 90000
xmin        = 500100
xmax        = ...
```

MVCC uses this information to determine whether a transaction should see a particular tuple version.

---

# 12. Transaction-ID Wraparound

Traditional PostgreSQL transaction IDs use a finite 32-bit ID space.

Eventually transaction IDs wrap around.

Conceptually:

```text
0
1
2
3
...
4 billion-ish
...
wrap around
```

PostgreSQL must prevent old transaction IDs from becoming ambiguous when this happens.

That is one of the critical responsibilities of vacuum.

This is why autovacuum is not merely a performance feature.

It is also part of PostgreSQL's **database safety mechanism**.

---

# 13. VACUUM FREEZE

PostgreSQL can mark sufficiently old tuple transaction information as frozen so those tuples don't need normal transaction-age comparisons forever.

Manual example:

```sql
VACUUM FREEZE employees;
```

You generally don't need to manually freeze every table. Normal vacuum/autovacuum performs freezing as tuples age.

You can inspect database transaction age:

```sql
SELECT
    datname,
    age(datfrozenxid)
FROM pg_database
ORDER BY age(datfrozenxid) DESC;
```

For tables:

```sql
SELECT
    relname,
    age(relfrozenxid)
FROM pg_class
WHERE relkind = 'r'
ORDER BY age(relfrozenxid) DESC
LIMIT 20;
```

A very high transaction age deserves investigation.

---

# 14. Anti-Wraparound Autovacuum

PostgreSQL can launch aggressive vacuum work to prevent transaction-ID wraparound.

You may see activity indicating something similar to:

```text
autovacuum: VACUUM ... (to prevent wraparound)
```

This should not simply be killed because it appears expensive.

If the database is approaching dangerous transaction ages, PostgreSQL prioritizes protecting the database from wraparound.

A DBA should instead investigate **why transaction age became so high**.

Potential causes include:

```text
Autovacuum unable to keep up
Long-running transactions
Old replication slots
Prepared transactions
Vacuum repeatedly blocked/interrupted
Poor vacuum configuration
Very high transaction workload
```

# 15. Important Autovacuum Monitoring Query

A practical starting point:

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

You can also calculate a rough dead-tuple percentage:

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    round(
        100.0 * n_dead_tup /
        NULLIF(n_live_tup + n_dead_tup, 0),
        2
    ) AS dead_tuple_pct,
    last_autovacuum
FROM pg_stat_user_tables
ORDER BY dead_tuple_pct DESC NULLS LAST;
```

Don't use the percentage alone. A 1% dead-tuple ratio on a billion-row table can still represent a huge amount of work.

For troubleshooting:

```sql

```

Or:

```sql
VACUUM (VERBOSE, ANALYZE) employees;
```

Verbose output can help you understand what vacuum actually processed.

# 17. VACUUM vs VACUUM FULL

| Feature                              | VACUUM         | VACUUM FULL         |
| ------------------------------------ | -------------- | ------------------- |
| Cleans obsolete tuples               | Yes            | Yes                 |
| Makes space reusable                 | Yes            | Yes                 |
| Shrinks physical table substantially | Usually no     | Yes                 |
| Rewrites table                       | No             | Yes                 |
| Blocking impact                      | Relatively low | High                |
| Routine maintenance                  | Yes            | No                  |
| Extra disk/work considerations       | Lower          | Significant rewrite |

Interview point:

> **Regular VACUUM is designed for routine concurrent maintenance. VACUUM FULL is a table rewrite and requires an exclusive lock, so it should be planned carefully in production.**

---

# 18. VACUUM vs ANALYZE vs REINDEX

Keep these three separate:

```text
VACUUM
   |
   +--> dead tuples / visibility / freezing

ANALYZE
   |
   +--> optimizer statistics

REINDEX
   |
   +--> rebuild indexes
```

Examples:

```sql
VACUUM orders;

ANALYZE orders;

REINDEX TABLE orders;
```

A common mistake is assuming `VACUUM` automatically solves every kind of index bloat. It doesn't.

# 19. Common Production Troubleshooting Flow

Suppose an application team says:

> "The orders table keeps growing and queries are becoming slow."

Start with:

```sql
SELECT
    n_live_tup,
    n_dead_tup,
    last_autovacuum,
    last_autoanalyze
FROM pg_stat_user_tables
WHERE relname = 'orders';
```

Then check long transactions:

```sql
SELECT
    pid,
    usename,
    state,
    now() - xact_start AS transaction_age,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Then active vacuum:

```sql
SELECT *
FROM pg_stat_progress_vacuum;
```

Then configuration:

```sql
SHOW autovacuum;
SHOW autovacuum_max_workers;
SHOW autovacuum_vacuum_scale_factor;
SHOW autovacuum_vacuum_threshold;
```

From there, determine whether the issue is:

```text
High write volume
        |
        +--> vacuum threshold too high
        |
        +--> autovacuum too slow
        |
        +--> insufficient workers/resources
        |
        +--> long-running transaction
        |
        +--> locking/blocking
        |
        +--> index/table bloat
        |
        +--> transaction age problem
```

# 20. Important Interview Questions

**Q: Why does PostgreSQL need VACUUM?**

Because PostgreSQL's MVCC implementation leaves obsolete tuple versions after updates/deletes. VACUUM makes that space reusable and performs transaction-ID maintenance needed to prevent wraparound.

**Q: Does VACUUM shrink the table?**

Regular `VACUUM` generally does not shrink the physical file significantly. It makes dead space reusable. `VACUUM FULL` rewrites the table and can return space to the OS.

**Q: Why can dead tuples remain even after autovacuum runs?**

One important reason is an old transaction/snapshot that still requires the old tuple versions. Vacuum cannot remove tuples that may still be visible.

**Q: Difference between VACUUM and ANALYZE?**

`VACUUM` performs storage/MVCC maintenance. `ANALYZE` updates statistics used by the query planner.

**Q: Should we disable autovacuum for a high-write table?**

Usually no. A high-write table often needs **more aggressive autovacuum tuning**, not less vacuuming.

**Q: What is transaction-ID wraparound?**

PostgreSQL transaction IDs have a finite ID space. PostgreSQL must freeze sufficiently old transaction information before wraparound can make transaction ordering ambiguous.

**Q: Why is autovacuum important even when performance looks fine?**

Because autovacuum is also responsible for transaction-ID freeze maintenance and wraparound prevention.

# 21. Scenario-Based Interview Question

**Scenario:**

```text
Table: transactions
Rows: 800 million
Updates/day: 50 million
Dead tuples continuously increasing
Autovacuum enabled
```

**How would you troubleshoot it?**

A strong answer would be:

```text
1. Check n_live_tup and n_dead_tup.
2. Check last_autovacuum and autovacuum_count.
3. Check pg_stat_progress_vacuum.
4. Look for long-running/idle-in-transaction sessions.
5. Review table-level autovacuum configuration.
6. Determine whether scale factor is too high for the table size.
7. Review available autovacuum workers and cost limits.
8. Check table and index growth/bloat.
9. Check transaction-ID age.
10. Tune the high-write table independently if required.
```

For example, rather than globally changing every table:

```sql
ALTER TABLE transactions SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_threshold = 5000,
    autovacuum_analyze_scale_factor = 0.01
);
```

Those numbers are only an **example**, not universal production values. The correct settings depend on write rate, table size, hardware, acceptable I/O, and how quickly autovacuum completes.

## 22. Architecture-Level Mental Model

Remember the entire topic as one flow:

```text
                 PostgreSQL MVCC
                       |
             UPDATE / DELETE occurs
                       |
                       v
                  Dead Tuples
                       |
          +------------+------------+
          |                         |
          v                         v
       VACUUM                    ANALYZE
          |                         |
          v                         v
 Reusable tuple space       Planner statistics
 Visibility maintenance
 XID freezing
          |
          v
    Autovacuum automates it
          |
          +---------------------------+
          |                           |
          v                           v
 Performance maintenance      Wraparound protection
```

### One-line interview summary

> **PostgreSQL uses MVCC, which creates obsolete tuple versions during updates and deletes. VACUUM makes obsolete space reusable and performs visibility/freezing maintenance, ANALYZE maintains optimizer statistics, and autovacuum automates these operations while also protecting the database from transaction-ID wraparound.**
