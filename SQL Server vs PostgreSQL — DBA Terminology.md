### The most important architecture translation

A DBA moving from SQL Server to PostgreSQL should **not** assume every SQL Server feature has a PostgreSQL feature with a different name.

The key mental mapping is:

| SQL Server DBA Thinking        | PostgreSQL DBA Thinking                              |
| ------------------------------ | ---------------------------------------------------- |
| Transaction Log                | **WAL**                                              |
| `.mdf / .ndf`                  | **Relation files / Tablespaces**                     |
| `.ldf`                         | **WAL files**                                        |
| Filegroup                      | **Tablespace** — approximate mapping                 |
| SQL Server Agent               | **pg_cron / pgAgent / external scheduler**           |
| DMVs                           | **`pg_stat_*` + system catalogs**                    |
| `sys.dm_exec_requests`         | **`pg_stat_activity`**                               |
| `sys.dm_tran_locks`            | **`pg_locks`**                                       |
| Query Store                    | **`pg_stat_statements`** — not a full 1:1 equivalent |
| Execution Plan                 | **`EXPLAIN / EXPLAIN ANALYZE`**                      |
| Index Rebuild                  | **`REINDEX`**                                        |
| Update Statistics              | **`ANALYZE`**                                        |
| Index fragmentation            | **Index/Table Bloat**                                |
| SQL Server cleanup/maintenance | **VACUUM + ANALYZE + REINDEX when needed**           |
| RCSI/Snapshot concepts         | **MVCC**                                             |
| Row versions in `tempdb`       | **Tuple versions inside PostgreSQL relations**       |
| Always On AG                   | **Streaming Replication + HA orchestration**         |
| AG Primary                     | **Primary**                                          |
| AG Secondary                   | **Standby**                                          |
| AG Listener                    | **Proxy / VIP / Load Balancer**                      |
| Log Shipping                   | **WAL Shipping**                                     |
| Transactional Replication      | **Logical Replication**                              |
| Log Backup                     | **WAL Archiving**                                    |
| Point-in-Time Restore          | **PITR**                                             |
| Login                          | **Role with LOGIN**                                  |
| `sysadmin`                     | **Superuser**                                        |
| Linked Server                  | **Foreign Data Wrapper (FDW)**                       |
| SQL Profiler/XEvents           | **Logging + statistics/extensions**                  |
| `tempdb`                       | **No single equivalent**                             |
| `DBCC CHECKDB`                 | **No single direct equivalent**                      |
| `sp_configure`                 | **`postgresql.conf` / `ALTER SYSTEM`**               |

A particularly important difference is **PostgreSQL VACUUM**. 

SQL Server DBAs coming into PostgreSQL should learn **MVCC → dead tuples → VACUUM → autovacuum → freezing → transaction-ID wraparound → bloat** as one connected topic. It is one of the biggest PostgreSQL-specific DBA areas.

Likewise, for SQL Server, the core chain is **transaction log → VLFs → log truncation → recovery model → log backup → backup chain → restore/PITR**.
